# cid-resilience

Paste a CID, get sampled retrieval evidence for how many independent copies of it exist and, with a second vantage, which responders are provably apart.

- Web app: https://sgtpooki.github.io/cid-resilience/ (a frozen snapshot is also on Filecoin Onchain Cloud, see [Hosting](#hosting))
- No backend. Everything runs in your browser against public IPFS primitives.
- No provider cooperation. Nothing to install on the storage provider side.

## What it measures

> Provenance: statements cited to P, D or G rows trace to the pinned sources in `research/sources-*.md`. Everything else here (engine behaviour, thresholds, sampling, scoring, clustering, the example numbers) is implementation-derived from `engine/` or INFERRED from the linked measurement reports, and is labelled evidence, not proof.


For one CID the app:

1. **Discovers** providers from IPNI (`cid.contact`) and delegated routing (`delegated-ipfs.dev`), merged by Peer ID. Either source alone is enough; delegated routing sometimes drops its CORS header and is skipped when that happens.
2. **Samples** the DAG: streams a CAR from the first provider that serves one, checks that the first block is the requested root, hash-checks the SHA-256 blocks (membership of later blocks in the DAG is not checked), keeps at most 64, and stops. Challenges are drawn uniformly from that prefix, so a large DAG's tail is never tested. That provider is marked `warmed` in the table.
3. **Challenges** each HTTP endpoint with random blocks (`GET /ipfs/{block}?format=raw`), timing time-to-first-byte against an interleaved `bafkqaaa` baseline, which a gateway answers without touching storage. The body is hashed against the CID.
4. **Probes bitswap-only peers** that advertise browser-dialable addresses (WebTransport, WebRTC-direct, WSS; implementation choice, G 4a/4b for the protocol) through helia, using libp2p ping as the baseline. The probe is timed to the first byte of the want-block response and the block is hash-checked. That first byte also includes the peer's bitswap engine scheduling delay (INFERRED from the measurements, not a sourced claim), so bitswap `on-demand` is unproven rather than caught.
5. **Clusters** endpoints by resolved IP (treated as one box) and by ASN (treated as one operator). Both are INFERRED heuristics: one IP can front several machines and one ASN hosts many tenants. Known CDN ASNs are labelled and excluded from the durable count.
6. **Bounds distance**: radius = min(102.1 km x baseline RTT in ms + 11 km, 20,015 km) is an upper bound on how far the responder is from you, assuming paths are fibre or slower (G 10a, 10b; the 11 km covers coordinate rounding). One vantage gives "N copies within X km of you".
7. **Merges vantages**: the share link carries every report. When someone opens it elsewhere and measures, two responders whose distance disks do not overlap are proven apart. The resilience score is the largest set of boxes that are pairwise proven apart, searched over the first 20 boxes (a lower bound beyond that), not the raw provider count.

Per provider you get one of: `advertised` (listed, never answered), `untested`, `unreachable`, `invalid` (answered, wrong bytes or 404), `on-demand` (right bytes, excess latency of 30 ms or more by default), `local` (right bytes, excess under 30 ms). Local and on-demand are latency classes; they are evidence about where the bytes came from, not proof.

## What it cannot tell you

- **Proxies closer than the threshold.** The default 30 ms excess allows an upstream within roughly 3,000 km. A provider relaying from a box in the same metro passes, as does one that flushes headers before fetching the body or that slows its own baseline. `on-demand` means "measurably slower than its own no-op", not "proven proxied": the same box can land on either side of the line from different vantages.
- **Small DAGs.** A CID with fewer than 3 SHA-256 blocks gets fewer than 3 challenge pairs per provider, so its timing is marked `weak` (as is any excess below -50 ms). The example below is a one-block CID.
- **Anything about tomorrow.** It is a point-in-time measurement, not a periodic proof like PDP or WindowPoSt (daily proving periods, D §2, P §4).
- **Separation from one vantage.** Every single-vantage disk contains you, so two providers can never be shown apart until a second located vantage is merged.
- **Honest vantages.** Vantage locations are self-reported and reports are unsigned. The app flags contradictory disks but cannot stop a lying vantage from manufacturing a separation.
- **Private fibre.** Like Benson et al. and Gondree & Peterson, it assumes the provider has no faster-than-Internet link between its sites, and that paths are fibre or slower (a microwave relay could look up to 1.47x closer).
- **Durability.** A CDN edge with a warm cache is a real copy right now and not one next week. It is counted separately.

The full comparison with PoRep and PDP is in [research/vs-porep.md](research/vs-porep.md), the attack table in [research/threat-model.md](research/threat-model.md), and a plain-language summary of what a result does and does not establish in [research/what-it-answers.md](research/what-it-answers.md). Every protocol claim traces to a pinned permalink and quote in [research/sources-porep.md](research/sources-porep.md), [research/sources-pdp.md](research/sources-pdp.md), or [research/sources-ipfs-geo.md](research/sources-ipfs-geo.md).

## CLI

```sh
node count-copies.mjs <cid> [--lat 50.1 --lon 8.7 --label frankfurt] [--out report.json] [--merge other.json]
ROUNDS=5 MAX_EXCESS_MS=30   # env overrides
node --test 'test/*.test.mjs'
```

Node 22 or newer, no dependencies. The CLI and the web app share `engine/`.

## Hosting

The app is plain static files (`index.html`, `app.js`, `engine/`). GitHub Pages serves `main` and is the only deployment that tracks the code. A snapshot was also uploaded to Filecoin Onchain Cloud (calibration, provider ezpdpz-calib2, data set 141, root CID `bafybeibqlycb6a2ag6tqzlvslxqbhjgc4suk3ghqtudsepkncu6s4uze3y`) and renders through inbrowser.link, but FOC uploads are paused until the measurement is solid; treat that CID as a frozen snapshot. Helia is loaded on demand from jsdelivr only when a bitswap-only peer is found; everything else is first-party code.

## Known gaps

From the review round on 2026-10-28, still open:

- Timing is a heuristic, not a proof: a proxy within ~3,000 km, one that flushes headers early, or one that slows its own baseline all pass as `local`.
- Only the first 64 blocks of a DAG are ever sampled.
- Bitswap excess includes the peer's bitswap engine delay and is not calibrated.
- Reports carry no freshness logic: a merged report shows what was true when each vantage ran.
- No link yet from an endpoint to its FOC provider ID or PDP proving state; the registry lookup in this README was done by hand.
